# Manuscript consistency and delivery

Load for substantial multi-section work, changes to shared results/objects, final-readiness checks, reviewer packages or requested submission materials. This is a bounded consistency workflow, not permission to rewrite a full manuscript, publish, or run new experiments.

## Authority and task coverage

Identify the current author-designated manuscript, controlled template, target institution/journal, article type, submission stage and specification version. Distinguish official requirements, author-confirmed project conventions, published samples and provisional defaults. A sample's appearance is not an official requirement. Material conflicts with an applicable official rule require disclosure/confirmation, not a silent change to a frozen template.

For major work scan relevant lifecycle areas: research question/outline; source acquisition and reading; translation/citation; evidence/data; experiment/FE/ML/statistics; formulas/figures/tables; body/abstract/conclusion; cross-references/appendices; reviewer response; document rendering; declarations/privacy and delivery. Mark non-applicable or unavailable areas. A short paragraph task should not generate a full intake or audit package.

## Argument and claim closure

- Link the research question to the actual method, evidence and bounded contribution. Do not invent a research gap or unsupported novelty because a narrative needs one.
- Check whether abstract, introduction promises, chapter summaries and conclusions refer to evidence actually reported in the body. Match the object, metric, condition, direction and key values, not just repeated words.
- Conclusions introduce no new measured result. Keep material qualifications established by the evidence; do not delete failure cases or assume a separate limitations section is required to state necessary conditions.
- Preserve technical terms, symbols, translations and comparison baselines using the existing terminology ledger. A style sample supplies writing patterns, not its research facts.

## Change propagation

For a changed source/result/definition, identify affected data transformations, equations, plots, tables, captions, body statements, abstract, conclusions, references, appendices and any reply quotes. Use stable IDs/anchors until numbering is final. Revalidate only affected dependencies unless a global change requires wider checks.

Distinguish unchanged facts, author-reported changes, edits inspected in current files and independently recomputed results. A plausible value or yesterday's generated PDF is not evidence of today's manuscript.

For object-heavy work use [equation-figure-table-integrity.md](equation-figure-table-integrity.md). Confirm that each callout resolves to the intended object and that caption numbers/terminology match. Updating fields can change pagination; do not promise stale page/line locations.

## Reviewer package coupling

Use [reviewer-driven-revision.md](reviewer-driven-revision.md) for scoped body amendments. When a package is requested, keep comment ID, actual author action, changed passage/evidence, clean manuscript, marked manuscript and response synchronized.

- Quote the actual current passage; do not claim a proposed experiment or edit has been completed.
- Compare against the archived submission baseline when marking changes; red text alone is not proof of revision.
- Ensure clean/marked copies contain equivalent final scientific content after accounting for deleted text and revision markup; differences of pagination or formatting are separate. Do not assume every journal requires color-only marking.
- After content edits, refresh reply quotations, counts, references and rendered location pointers. Each reviewer receives a self-contained answer; do not use another reviewer's answer as an inaccessible substitute.
- Apply available specialist consistency scripts only to supported formats and inspect their scope; a LaTeX checker is not a Word checker. Missing script support remains a manual/unavailable check, not a passed one.

## Submission and declarations: only when applicable

Check the actual current target/stage requirements before assembling a package. Cover letters, highlights, graphical abstracts, anonymized copies, data/code statements, supplements and checklists may be required, optional, conditional or inapplicable. Do not create all of them by default for a thesis paragraph.

Never invent author names/order/approval, affiliations, contribution roles, grants, conflicts, ethics IDs, permissions, exclusive-submission facts, repository identifiers or AI-use declarations. Draft unknown facts as clearly marked author confirmations; do not state their absence as a verified negative.

Human authors retain responsibility for scientific judgments, attribution and the final manuscript. AI-supported outlines, interpretations or candidate wording are not verified scholarly findings. Do not minimize prior contributions to manufacture novelty; identify the source actually read and any reused third-party figure/wording permissions. Check applicable current AI policies when such compliance is requested instead of treating another skill's policy summary as authoritative.

Data/code availability must describe actual artifacts, versions, location and access conditions. Public, controlled, third-party and request-based access are different. A local dataset is not publicly deposited; a URL does not establish anonymous reviewer access. Respect ownership, embargo and licensing. Public release, upload, submission, library writes and external transmission require the relevant authorization.

If anonymity is required, inspect manuscript metadata, acknowledgments, tracked changes/comments and attached files as applicable. Do not remove authorship/ethics information from the authoritative original merely to prepare an anonymous copy.

## Document and delivery checks

Use the DOCX/PDF specialist workflow appropriate to create/convert/revise. Preserve originals by default. Selective local edits need affected-page visual review plus structural checks on unaffected content; global style/fields/numbering changes or a final audit can require whole-document review.

Record separately:

| Dimension | Evidence required to claim checked |
|---|---|
| Source/scientific | Actual source/evidence review and its scope; unresolved scientific judgments |
| Numeric | Defined inputs, operations/tolerances and observed comparisons |
| Structure | Actual editable objects, numbering, fields, references and file validity |
| Visual | Rendered pages/figures inspected at the intended output size |
| Package/administrative | Actual required files and author-confirmed facts, access/permission state |

Use existing readiness labels consistently: `PASS`, `WARN`, `BLOCK`, `UNAVAILABLE`, `NOT_APPLICABLE`. A missing renderer is `UNAVAILABLE` for visual review, not compliance. A successful installer proves packaging/install mechanics, not native client discovery or tool permissions. A structural pass does not certify the science.

Deliver the requested files with concise scope, authoritative input/version, checks actually run and material unresolved items. Do not claim submission-ready when a required dimension is blocked or unavailable. Do not expose private manuscripts, datasets, local credentials or library keys in public reports or repositories.

## Maintenance closure

When changing this skill, use [systematic-integration-map.md](../meta/systematic-integration-map.md). Check the full lifecycle for impact instead of only the newly requested feature. Record adopted source rules and deliberate exclusions; update their callers and remove contradictions. Keep the router small, use conditional references, and distinguish structural tests, behavioral cases, numeric tests, rendered artifacts and native-client tests. No external skill is a required dependency solely because its principles informed a rule.
